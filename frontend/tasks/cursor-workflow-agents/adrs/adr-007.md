# ADR-007: Automatic PRD Re-run After Rejection with Feedback

## Status

Accepted

## Date

2026-05-20

## Context

The PRD requires reject-with-feedback and re-run before approval. Open question #4 asked whether re-run is automatic or manual. User action required for accountability, but friction on reject should be low.

## Decision

On **Reject with feedback**, Pulse immediately enqueues a **new PRD agent run** with the feedback appended to the agent prompt context (along with slug, directive, branch, and prior draft reference). UI transitions to `running` without a separate "Run again" click. User may still **cancel** the new run if needed.

Store rejection feedback on the failed/rejected run record for audit; link `supersedesRunId` on the new run.

## Alternatives Considered

### Alternative 1: Manual Re-run Only

- **Description**: Save feedback; user clicks "Executar novamente".
- **Pros**: Maximum explicit consent per run.
- **Cons**: Extra step; lower completion rate metric.
- **Why rejected**: Stakeholder chose automatic re-run during TechSpec clarification.

### Alternative 2: Confirmation Dialog Before Re-run

- **Description**: Modal summarizing feedback then enqueue.
- **Pros**: Prevents accidental loops.
- **Cons**: Extra click on every reject; still needs cancel affordance.
- **Why rejected**: Not selected; cancel covers mistaken rejects.

## Consequences

### Positive

- Faster rework cycles aligned with ≥20% PRD cycle time goal.
- Clear run lineage via `supersedesRunId` for rework rate metric.

### Negative

- Risk of runaway loops if user repeatedly rejects; mitigation: soft cap or warning after N consecutive rejects (configurable constant, not blocking MVP).

### Risks

- Accidental reject triggers costly agent run; mitigation: undo window optional post-MVP; MVP relies on deliberate reject control placement.

## Implementation Notes

`RejectPrdWithFeedbackUseCase` writes feedback, marks prior run, calls `StartPrdAgentRunUseCase` in same transaction flow. Stream UI resets to new `runId`.
