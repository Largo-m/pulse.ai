# ADR-003: Pulse-Internal Artifact Storage by Project and Slug

## Status

Accepted

## Date

2026-05-19

## Context

Early drafts assumed workflow artifacts would live in the imported repository (e.g. under a tool-specific folder in the Git tree). Stakeholders require **all workflow artifacts to remain inside Pulse**, organized by **mapped project** and **workflow slug**, so delivery artifacts are not mixed into application source trees and ownership stays with the orchestration product.

## Decision

Store **all workflow artifacts in Pulse-managed storage**, partitioned as:

1. **Mapped project** — the imported/local project identity Pulse already tracks in the orchestrator (stable project id, not only filesystem path).
2. **Workflow slug** — user-defined identifier for a feature/initiative within that project.
3. **Artifact set** — per slug, at minimum `_prd.md`, `adrs/`, run metadata, and execution stream history for the PRD phase; future phases add their artifacts under the same slug.

Artifacts are **not written into the imported repository** by default. The UI and APIs resolve content from Pulse storage using project + slug. Users browse and approve artifacts entirely within Pulse.

## Alternatives Considered

### Alternative 1: Artifacts in the Git Repository

- **Description**: Write `_prd.md` and ADRs under a hidden folder in the cloned/local project directory.
- **Pros**: Artifacts versioned with code; familiar to teams using repo-based docs.
- **Cons**: Pollutes app repos; permission and sandbox complexity; conflicts with Pulse as system of record; harder to enforce PT-BR/orchestration-only data boundaries.
- **Why rejected**: Conflicts with requirement that artifacts live inside Pulse.

### Alternative 2: Flat Global Store (No Project Partition)

- **Description**: Single Pulse folder keyed only by slug.
- **Pros**: Simple layout.
- **Cons**: Slug collisions across projects; weak multi-project UX for tech leads.
- **Why rejected**: Does not match mapped-project mental model in the orchestrator.

## Consequences

### Positive

- Clear ownership: Pulse is the source of truth for workflow artifacts.
- Safer separation from customer codebases (no accidental commits of draft PRDs).
- Natural fit for project switcher and recent-projects sidebar.

### Negative

- Teams that want repo-versioned PRDs need a future export/sync capability (out of MVP).
- Backup and portability depend on Pulse data location (product must communicate how workflows are preserved).

### Risks

- Users expect files in Git; mitigation: explicit copy that artifacts live in Pulse; optional export in a later phase.
- Project remapping (re-import path) must preserve artifact association; mitigation: stable internal project id.

## Implementation Notes

Physical storage layout and sync/export belong in TechSpec. Product contract: **project id + slug** uniquely identifies a workflow’s artifact bundle inside Pulse.
