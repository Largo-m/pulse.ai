# ADR-001: Native Pulse Cockpit for Cursor Workflow Orchestration

## Status

Accepted

## Date

2026-05-19

## Context

Pulse.AI is building an agentic orchestration desktop experience for the delivery pipeline (PRD → TechSpec → Tasks → execution → QA → Review). Stakeholders need Cursor-powered specialist agents to run inside the workflow with human approval gates, live execution visibility, and artifacts kept **inside Pulse** per mapped project and slug. Three product approaches were evaluated: a native Pulse control plane, delegation to an external CLI/daemon, and a Cursor Cloud-first model.

## Decision

Adopt a **native Pulse cockpit** as the primary product model. Pulse orchestrates each pipeline phase, requires explicit user approval of phase artifacts before advancing, persists workflow outputs in **Pulse-managed storage** (partitioned by mapped project and workflow slug), and executes Cursor specialist agents with a live in-app execution stream. Pulse owns orchestration, gating, observability, and artifact custody.

## Alternatives Considered

### Alternative 1: External CLI / Daemon Wrapper

- **Description**: Pulse delegates execution and state to an external orchestration CLI; UI focuses on attach, approve, and minimal customization.
- **Pros**: Faster initial delivery; reuses mature run lifecycle APIs elsewhere.
- **Cons**: Weaker differentiated UX for tech leads; harder to tailor approval flows and streaming to Pulse; coupling to external tool release cadence.
- **Why rejected**: Does not fully meet the goal of Pulse as the primary orchestration and artifact surface.

### Alternative 2: Cursor Cloud-First

- **Description**: Prioritize cloud-hosted Cursor agents; Pulse acts as monitoring and approval dashboard.
- **Pros**: Scales parallel execution; reduces local machine burden.
- **Cons**: Higher network dependency; weaker local-first story; artifact flows may feel disconnected from mapped desktop projects.
- **Why rejected**: Conflicts with local-project-first orchestrator experience and in-app streaming as the primary execution view.

## Consequences

### Positive

- Tech leads can run and supervise agent phases from Pulse without context-switching; the first delivery targets the PRD phase (see ADR-002).
- Phase gates create clear accountability aligned with team delivery practices.
- Pulse-internal artifacts (ADR-003) keep orchestration data separate from application repositories.

### Negative

- Pulse must own more orchestration behavior (status, errors, retries, approval UX) than a thin-wrapper approach.
- A full-pipeline release would increase failure surface; **ADR-002** limits the first delivery to PRD only.

### Risks

- Users may expect Cursor IDE parity; mitigation: position Pulse as orchestration cockpit, not IDE replacement.
- End-to-end delivery metrics depend on factors outside Pulse; mitigation: measure PRD phase cycle time inside Pulse.

Product requirements are in `_prd.md`. Technical design belongs in a subsequent TechSpec.
