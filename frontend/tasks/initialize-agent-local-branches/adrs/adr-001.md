# ADR-001: Reactive Local Branch Loading per Project

## Status

Accepted

## Date

2026-05-18

## Context

The "Novo agente" modal currently shows a hardcoded branch list unrelated to the user's selected local project. Users need to pick a real local Git branch when initializing an agent so the chosen branch is stored as agent metadata. The product does not require checkout or repository mutation in this phase. Stakeholders confirmed local-only branches, HEAD as default on project change, and explicit UI states for loading, non-Git projects, and read failures.

## Decision

Adopt **reactive branch loading per project** for MVP:

- When the modal opens or the user changes the selected project, load **local branches only** from that project's repository path.
- Pre-select the **currently checked-out branch (HEAD)** after each successful load.
- Store the user's branch choice as **agent metadata only**; do not change the working tree or perform checkout.
- Show a **disabled branch field with loading indicator** while branches load.
- Show a **disabled branch field with explanatory copy** when the folder is not a Git repository or when branch enumeration fails.

## Alternatives Considered

### Alternative 1: Reactive loading + per-project memory

- **Description**: Same as the chosen approach, but persist the last branch selected per project and prefer it over HEAD on subsequent opens.
- **Pros**: Faster repeat setup for power users.
- **Cons**: Extra precedence rules (saved choice vs HEAD); larger MVP scope.
- **Why rejected**: Deferred; HEAD default is sufficient for first release.

### Alternative 2: On-demand refresh only

- **Description**: Keep a static branch list until the user explicitly taps "Refresh branches"; changing project does not auto-reload.
- **Pros**: Fewer automatic operations; simpler mental model for edge cases.
- **Cons**: Stale lists after project switch; easy to initialize an agent against the wrong branch.
- **Why rejected**: Conflicts with the primary flow (project switch must update branches).

## Consequences

### Positive

- Branch choices reflect the real local repository state at initialization time.
- Clear disabled states reduce confusion for non-Git folders and failures.
- Narrow MVP scope (metadata only) avoids coupling to agent runtime checkout behavior.

### Negative

- Users who always work on a non-HEAD branch must change the selection each time (no memory in MVP).
- Brief loading state on every project switch may feel repetitive on slow disks.

### Risks

- Users may assume selecting a branch checks it out; copy and disabled/error messaging must clarify metadata-only behavior.
- Very large numbers of local branches could make the dropdown hard to scan (mitigation: defer sorting/search to a later phase if reported in testing).

## Implementation Notes

- Enumerate branches from `LocalProjectEntity.absolutePath` associated with the selected project id.
- Reload triggers: modal open (initial project), project dropdown change.
- Branch list scope: local heads only (no remote-tracking refs).
