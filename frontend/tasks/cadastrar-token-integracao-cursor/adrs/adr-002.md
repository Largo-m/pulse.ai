# ADR-002: Cursor Settings as Modal Sheet Without Dedicated Route

## Status

Accepted

## Date

2026-05-22

## Context

The orchestrator shell currently exposes only `/orchestrator` and import routes. The PRD does not mandate a full-page settings area. Desktop Flutter already uses dialogs for destructive confirmation (`PrdReviewUnsavedOverwriteDialog`). Adding a named route solely for a small credential form increases router surface without enabling deep links in MVP.

## Decision

Present Cursor integration settings as a modal bottom sheet (or platform-appropriate dialog-style sheet) over the orchestrator workspace. Open via callbacks from the gear icon and banner CTA; dismiss with `Navigator.pop`. Do not add `RoutePaths` / `RouteNames` entries in MVP.

## Alternatives Considered

### Alternative 1: Dedicated named route

- **Description**: Register `/orchestrator/settings/cursor` in the app router.
- **Pros**: Deep-linkable; familiar for large settings apps.
- **Cons**: New route tests, shell integration, and navigation constants for a single form; YAGNI for MVP.
- **Why rejected**: No PRD requirement for deep links; modal satisfies both entry points.

### Alternative 2: End drawer / side panel

- **Description**: Persistent side panel in orchestrator shell.
- **Pros**: Keeps context visible.
- **Cons**: Layout work on `WorkflowPrdWorkspace`; no existing drawer pattern in orchestrator.
- **Why rejected**: Higher UI cost than modal for a infrequently edited secret field.

## Consequences

### Positive

- Fastest path to wire gear + banner; no router churn.
- Aligns with existing dialog patterns in orchestrator.

### Negative

- No URL/deep link to settings until a future route is added.
- Modal must receive `CursorConnectionCubit` via context/`BlocProvider.value`.

### Risks

- Small viewports: sheet height must scroll — use `isScrollControlled` and DS spacing tokens.

## Implementation Notes

Extract `CursorIntegrationSettingsSheet.show(BuildContext context)` similar to `PrdReviewUnsavedOverwriteDialog.show`.
