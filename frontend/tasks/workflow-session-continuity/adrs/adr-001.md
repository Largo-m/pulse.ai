# ADR-001: Last Completed Session Auto-Restore

## Status

Accepted

## Date

2026-05-22

## Context

PRD workflow owners lose terminal logs, conversational context, and artifact alignment when navigating away or restarting Pulse.ai. Runs and stream events already persist in Hive and JSONL, but `PrdWorkflowCubit.bindWorkflow` only restores workflow phase status. The product requires a coherent snapshot of the latest **terminal** run (`completed`, `failed`, or `cancelled`) per `workflowKey`, with a distinct in-progress-only presentation when the latest run is still active.

## Decision

On every PRD workflow open, automatically resolve and hydrate the **most recent finalized run** for that workflow: terminal log lines, derived conversation messages, and artifact presentation tied to the same `runId`. If the latest run is non-terminal, show in-progress UI only (no partial log or conversation replay). Scope is PRD phase MVP; TechSpec phase follows the same contract later.

## Alternatives Considered

### Alternative 1: Manual “Load history” action

- **Description**: User triggers restore explicitly.
- **Pros**: Simpler first implementation; avoids open-time latency.
- **Cons**: Violates PRD auto-restore; increases time-to-context.
- **Why rejected**: Conflicts with primary user stories and success metrics.

### Alternative 2: Run timeline picker on open

- **Description**: Let user choose among finalized runs when opening a workflow.
- **Pros**: Solves multi-run audit needs immediately.
- **Cons**: Scope creep; slower default path.
- **Why rejected**: Deferred to Phase 3 in PRD.

### Alternative 3: Live SSE catch-up for active runs

- **Description**: Reconnect stream on return and backfill events.
- **Pros**: Continuous live experience.
- **Cons**: Complex; risks misleading partial state.
- **Why rejected**: Explicit non-goal for MVP.

## Consequences

### Positive

- Meets “blank workflow” anxiety goal without new persistence substrate.
- Reuses `listRunsForWorkflow` + `listStreamEvents` ordering already in repositories.

### Negative

- Open path gains I/O and mapping work; must cap event volume (see ADR-004).
- Active-run UX remains status-only until run completes.

### Risks

- Incorrect run binding across workflows — mitigate with strict `workflowKey` filtering and single `restoredRunId` in state.
- Stale in-progress after offline completion — mitigate with cloud reconciliation (ADR-003).

## Implementation Notes

- Terminal statuses: `PrdRunStatus.isTerminal` (`completed`, `failed`, `cancelled`).
- Pick first run in `listRunsForWorkflow` descending `startedAt` that is terminal; if none, empty state.
- If latest run is non-terminal, skip hydration; emit in-progress session mode.
