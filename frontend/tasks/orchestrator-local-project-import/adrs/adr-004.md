# ADR-004: Normalized Absolute Path as Project Identity

## Status

Accepted

## Date

2026-05-15

## Context

Re-import must not duplicate rows. Active selection and persistence must reference a stable key. Phase 2–3 agents will bind to `absolutePath` on disk.

## Decision

Use the **normalized absolute path** as `LocalProjectEntity.id`:

- Resolve to absolute path via `path` package (`canonicalize` / `normalize` where the platform allows).
- Same normalized path ⇒ same id; re-import updates `lastAccessedAt` and promotes to top.
- `displayName` = last path segment (`basename`) at import time; not used as id.

## Alternatives Considered

### Alternative 1: Hash of path

- **Description**: `id = sha256(normalizedPath)`.
- **Pros**: Fixed-length id; path not stored as key.
- **Cons**: Still need path stored; extra indirection for debugging.
- **Why rejected**: Path is required for agents anyway; hash adds no MVP benefit.

### Alternative 2: UUID on first import

- **Description**: Opaque id; path is mutable field.
- **Pros**: Survives folder moves with migration logic later.
- **Cons**: Dedupe requires path scan; migration not in MVP.
- **Why rejected**: PRD defers path validation and move handling to Phase 2.

## Consequences

### Positive

- Trivial dedupe and equality checks.
- No separate id generation service.

### Negative

- Folder move on disk leaves stale path until Phase 2 validation.
- Platform-specific path normalization edge cases require tests.

### Risks

- Symlinks / different spellings of same folder — mitigate with canonicalization in `ImportLocalProjectUseCase` and unit tests per OS where feasible.

## Implementation Notes

- Extract `ProjectPathNormalizer` as a small domain helper or private method on use case.
- Invalid path on disk: MVP allows selection silently (PRD); Phase 2 adds warning.
